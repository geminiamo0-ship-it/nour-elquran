## 1. النتيجة المطلوبة ونطاق الخطة

نحوّل «دفتر الحصص» إلى أرشيف تعليمي تفاعلي لكل طالب: يفتح الحصة، يرى آخر تقرير اعتمده الشيخ، يراجع الآيات وتصحيحاتها داخل قارئ المصحف نفسه، ويضيف ملاحظاته الخاصة في طبقة مستقلة. الواجب المرتبط بالحصة يُفتح في «تدريباتي». ثم نربط هذه الرحلة بالخادم ضمن **مرحلة Backend واحدة مقسّمة إلى PRs مترتبة**.

الخطة تشمل تجهيز واجهة الدفتر، نموذج البيانات، الصلاحيات، API، النشر والمراجعات، التخزين والصوتيات، الفصل المباشر، الاعتمادات مع الحجز والحضور والاشتراكات والإشعارات، واختبارات الإطلاق. لا تعني إضافة هذا المستند إنشاء قاعدة بيانات أو حساب خدمة أو إرسال رسالة أو دمج ميزة.

| التصنيف | المعنى |
|---|---|
| معتمد | قرار منتج موجود في متطلبات المالك ومراجع المشروع |
| مقترح هندسي | طريقة تنفيذ موصى بها في هذه الخطة، تُثبت في ADR/عقود واختبارات قبل تنفيذها |
| قرار تشغيلي مطلوب | اختيار محدد يُحسم قبل الميزة التابعة له، ولا يوقف المهام المستقلة |
| منفذ ومفحوص | كود موجود في المرجع المذكور؛ ليس بالضرورة منشورًا أو مخزنًا على الخادم |

## 3. ثوابت المنتج المعتمدة

1. **مصحف واحد لكل طالب**؛ النص والصفحات مرجع ثابت، والطبقات التعليمية منفصلة عنه.
2. المصحف للقراءة والتراكم؛ تدريباتي للتنفيذ والواجب؛ دفتر الحصص لما حدث في الحصة.
3. دفتر الحصة يعرض نطاقها عبر نفس `ReaderPrintedPage / QuranAyahOverlay / QuranInk`، ولا ينشئ نسخة مصحف أو مصدر ملاحظات مكررًا.
4. حساب واحد يمكنه إدارة أكثر من طالب؛ لا لوحة مستقلة لولي الأمر.
5. الطالب يرى **آخر إصدار منشور ومعتمد** لكل تقرير، ولا يرى المسودات أو تاريخ نسخ التقرير الخاص بالتدقيق.
6. الحفظ والتلاوة والتجويد ثلاث درجات مستقلة من 10؛ `null` = لم يُقيَّم، وليس صفرًا. لا متوسط تلقائي ولا رسم أكاديمي بديل للجدول المعتمد.
7. انتهاء الحصة والحضور ونشر التقرير حالات مستقلة؛ قد تنتهي الحصة والتقرير قيد الإعداد.
8. طبقة الحصة الأصلية للقراءة، وطبقة الطالب الشخصية قابلة للتحرير وخاصة افتراضيًا.
9. المشاركة اختيار لمحتوى محدد، ومعاينة ومستلم مصرح به وتأكيد صريح؛ لا مشاركة تلقائية لكل الدفتر.
10. إنجاز تدريب أو Checkbox أو تسليم صوت لا يساوي إتقانًا أو درجة؛ اعتماد الشيخ هو المرجع التعليمي.
11. القرآن لا يُولَّد ولا يُعدَّل بواسطة AI. الذكاء الاصطناعي لاحقًا لمسودات يراجعها الشيخ.
12. حفظ علامات المصحف وPDF/PNG **لا يجيز تسجيل صوت/فيديو الحصة**.

المراجع: [فصل الأقسام](STUDENT_TRAINING_NOTEBOOK_INFORMATION_ARCHITECTURE.md)، [المصحف الموحد](QURAN_CANONICAL_MUSHAF_AND_LESSON_VIEWS.md)، [التقارير #15](https://github.com/geminiamo0-ship-it/nour-elquran/issues/15)، [القرارات الأصلية #3](https://github.com/geminiamo0-ship-it/nour-elquran/issues/3).

## 4. تجربة دفتر الحصص من البداية للنهاية

### 4.1 فتح الدفتر واختيار الحصة

- العنوان «دفتر الحصص»؛ أحدث الحصص المكتملة أولًا. يظهر التاريخ، الشيخ، النطاق القرآني، وحالة التقرير/الأرشيف.
- نستخدم تحميلًا تدريجيًا وقائمة بسيطة. لا نضيف فلاتر أو رسومًا إلى جدول «تقدمي وتقاريري»؛ مواصفاته المعتمدة تظل مستقلة.
- رابط من «حصصي» أو «تقدمي» يفتح الحصة المحددة مباشرة، بعد التحقق من الطالب والحصة على الخادم.
- الطالب الجديد يرى حالة فارغة حقيقية. لا حصص ولا أسماء شيوخ ولا درجات مختلقة.
- الحصة المكتملة بلا تقرير: «انتهت الحصة — التقرير قيد الإعداد». تظل ملاحظات الطالب الخاصة متاحة إذا كانت مرتبطة بالحصة، ولا تظهر علامات الشيخ غير المنشورة.

### 4.2 محتوى الحصة

| المنطقة | المحتوى |
|---|---|
| رأس الحصة | الوقت والمنطقة الزمنية، الشيخ الذي درّس فعلًا، النطاق، وحالة التقرير |
| تقرير الشيخ | الدرجات الثلاث إن وُجدت، ما تمت قراءته وحفظه ومراجعته، الأخطاء، نقاط القوة والتوجيهات |
| المصحف | صفحات الحصة فقط، تمييز الآيات، العلامات والملاحظات المنشورة، والتنقل بين صفحات النطاق |
| الملاحظات | «ملاحظات الحصة» للقراءة و«ملاحظاتي» للإضافة والتعديل والحذف |
| إجراءات | فتح الموضع في المصحف، فتح الواجب في تدريباتي، مشاركة المحدد، تنزيل الأرشيف عند جاهزيته |

نطاق الحصة يقبل أكثر من سورة وصفحة ومجموعة آيات. لا نكتفي بحقل `page` واحد الموجود في نموذج التدريب الحالي؛ الصفحات تُشتق من خريطة الطبعة المعتمدة، ولا تُستنتج من وصف عربي حر.

### 4.3 الطبقات والتفاعل

- أدوات الظهور: «الملاحظات الأصلية»، «ملاحظاتي»، «إخفاء/إظهار الكل». إخفاء طبقة لا يحذفها.
- مسح/ممحاة/Undo الطالب تعمل على إضافاته المسموح بها فقط؛ لا تمس تقرير الشيخ أو العلامات الأصلية.
- قلم وماركر وملاحظة مرتبطة بآية/كلمة/صفحة، بنفس تفاعل المصحف المعتمد: ضغطة للتحديد وضغطتان للملاحظة؛ لوحة أدوات عمودية دون تصغير الصفحة.
- «إعادة ضبط العرض» يعيد المرشحات والموضع، ولا يمسح البيانات.
- تمييز المؤلف والنوع بنص وأيقونة مع اللون؛ لا نعتمد على اللون وحده.
- الهاتف: المصحف في المقدمة، تفاصيل التقرير والملاحظات داخل لوحات قابلة للطي؛ القلم وS Pen مع الفصل اليدوي بين الرسم والتقليب.
- لوحة المفاتيح وقارئ الشاشة وحالة التحميل والخطأ و`prefers-reduced-motion` جزء من القبول.

### 4.4 الملاحظات الشخصية والمشاركة

الطالب يكتب مسودة خاصة ويستطيع اختيار ملاحظات أو مقتطف صفحة محدد. المعاينة تُظهر ما سيصل، الآيات، والشيخ المستلم. بعد «إرسال للشيخ» ينشئ الخادم Snapshot مشاركة منفصلًا؛ تعديل الأصل لاحقًا لا يغير المحتوى الذي أُرسل.

قرار **إلغاء المشاركة وحذف النسخة المشتركة ومدة احتفاظ الشيخ** ما زال يحتاج سياسة محددة قبل تفعيل المشاركة الحقيقية؛ هذه الخطة تقترح إلغاء الوصول المستقبلي عبر المنصة مع الاحتفاظ بتدقيق محدود وفق سياسة الاحتفاظ. لا ندعي استرجاع نسخة سبق تنزيلها أو مشاهدتها. صلاحية ولي الأمر للتحرير/المشاركة باسم طفل تُحسم مع تصميم جلسة الطفل؛ لا تُستنتج من زر داخل الواجهة.

### 4.5 PDF وPNG

- «نسخة الحصة الأصلية»: آخر محتوى منشور ومعتمد، من Snapshot وطبعة ثابتين.
- «نسخة مع ملاحظاتي»: نفس الأصل مع Snapshot محدد من الطبقة الشخصية، بتسمية واضحة أنها إضافات لاحقة.
- PDF/PNG مشتقات للعرض والتنزيل؛ JSON المنظم والمراجع وإصدارات النشر هي مصدر الحقيقة.
- إنشاء التصدير Job بحالات `queued / rendering / ready / failed`؛ لا زر تنزيل وهمي.
- فشل التصدير لا يخفي التقرير أو المصحف التفاعلي. Retry لا ينشئ تصديرات متكررة لنفس المدخلات.
- أي تصحيح منشور يجعل روابط النسخة السابقة غير متاحة عبر API الطالب؛ لا نمحو سجل التدقيق الخاص بالموظفين المصرح لهم. الملفات الحساسة لا تُخزن في Cache عام؛ نحدد `Cache-Control` وعزل Cache بحسب الهوية والطالب والإصدار.

## 5. حالات الواجهة وعقد الحفظ

| الحالة | السلوك المطلوب |
|---|---|
| لا حصص | رسالة فارغة وروابط الحجز/المصحف المناسبة للحالة |
| تقرير قيد الإعداد | بيان واضح بلا درجات أو ملاحظات من المسودة |
| تقرير منشور | آخر إصدار فقط مع النطاق والطبقات المنشورة |
| أرشيف ناقص/تالف | يظل التقرير ظاهرًا، ونوضح الجزء المتعذر وإعادة المحاولة |
| جارٍ الحفظ | لا نظهر «محفوظ» قبل ACK دائم من الخادم |
| حفظ متعذر | المسودة تبقى قابلة للاسترداد مع Retry |
| تعارض إصدار | لا نستبدل تعديل جهاز آخر بصمت؛ نعيد القراءة أو نعرض تعارضًا |
| Offline | القراءة مما سُمح بتخزينه؛ الإضافات «بانتظار المزامنة»، بلا ادعاء إرسال |
| وصول منتهٍ | إزالة المحتوى المحمي من العرض ومنع العمليات وإعادة التحقق |
| تبديل الطالب/خروج | إلغاء الطلبات القديمة، وقف الميكروفون، فصل الاتصالات ومسح الحالة الحساسة |

اقتراح v1: لا تخزين Offline دائم لمحتوى الأطفال على جهاز مشترك افتراضيًا. يمكن تمكين Outbox محلي خاص بعد تحديد الموافقة وسياسة الجهاز؛ يبقى المسار الأول Online مع مسودة مؤقتة صريحة. لا نَعِد بأن الذاكرة المحلية تحفظ العمل بعد إغلاق الجهاز.

## 7. توزيع المسؤوليات في الباك إند — مقترح هندسي

| المكوّن | مسؤولية محددة ومصدر الحقيقة |
|---|---|
| Next.js الحالي | عرض الواجهات والجلسة عبر Adapter؛ لا مفاتيح خدمة داخل المتصفح |
| API على Cloudflare Worker | التحقق من الهوية، تفويض الطالب/المورد، Schema validation، Use cases وRate limits |
| Auth داخل Workers | هوية الحساب البالغ/الموظف، والتحقق من جلسة الدخول |
| D1 SQLite | الملكية والأدوار والحصص والتقارير والإصدارات والتكليفات والمشاركات والحجز والحقوق المالية |
| Lesson Durable Object بعد Spike | ترتيب عمليات الحصة المباشرة، ACK بعد حفظ دائم، Replay وختم الحالة |
| R2 عام | ملفات القرآن المعتمدة فقط، بإصدار ومصدر وتحقق |
| R2 خاص | Snapshots والتصديرات والصوتيات المصرح بها؛ لا روابط عامة |
| Outbox ثم Queues | التصدير والإشعارات ومعالجة الملفات، مع تكرار آمن وإعادة تشغيل |
| Cloudflare RealtimeKit | الصوت والفيديو المباشر؛ الاتصال به مباشرة من العملاء المصرح لهم |

لا ننشئ StudentDO أو TeacherScheduleDO افتراضيًا. الحجز والأرصدة ونشر التقارير تظل معاملات D1. استخدام DO للحصة قرار تنفيذ مرتبط بنتيجة Spike وADR؛ لا يُحوّل كل CRUD إلى DO. استمرار حصة مفتوحة عند تعطل خدمة خارجية لا يجيز نشر تقرير أو منح دخول جديد دون تحقق محفوظ وسياسة صريحة.

**النشر:** إصلاح #105 مدمج في main (`df284bcf`) ويضبط Next.js static export وWorkers Static Assets، مع API مستقل. نحتفظ بهذا المسار أثناء تأسيس الخادم؛ لا ندعي تحقق نشره من مجرد الدمج. أي انتقال إلى SSR واختيار Adapter Cloudflare يبقى في [#40](https://github.com/geminiamo0-ship-it/nour-elquran/issues/40)؛ لا نربط نجاح الباك إند بتغيير Framework أو استضافة غير مُتحقق منها. لا نشغّل Vercel Previews تلقائيًا؛ وضعها الحالي مغلق للمحافظة على الحصة.

## 8. الهوية والصلاحيات

**`auth_user_id ≠ learner_id`.** اختيار ملف من القائمة ليس إثبات صلاحية. كل عملية تربط الحساب الموثق بالطالب والمورد والفاعل والدور ووقت الصلاحية.

حساب ولي الأمر مخوّل بإدارة أطفاله طبقًا للصلاحيات المعتمدة. عزل الأشقاء يعني عدم خلط بياناتهم وطلباتهم وطبقاتهم؛ لا نزعم أن تفويض الخادم يمنع صاحب الحساب المخوّل من تبديل الملف وقراءة طفل آخر يملكه. منع الطفل من الوصول لملف أخيه يحتاج جلسة/وضع طفل مقيدًا وإعادة تحقق لتبديل الملف؛ آليته قرار مستقل قبل الاستخدام الحقيقي على جهاز مشترك.

| الفاعل | القراءة | الكتابة/الإجراءات | المنع |
|---|---|---|---|
| صاحب الحساب الموثق | طلابه حسب الصلاحية والسياق المحدد | إعدادات الحساب والطالب؛ التحرير/المشاركة باسم الطفل بحسب السياسة | حسابات أخرى أو صلاحيات موظفين |
| جلسة الطالب المقيدة إن فُعّلت | بيانات الطالب المربوط بالجلسة | ملاحظاته ومسوداته وتسليمه المصرح | تبديل طالب أو دفع أو وصول أسري بلا إعادة تحقق |
| الشيخ الأساسي | سجل تعليمي مصرح ومشاركات موجهة له | تقارير وتكليفات وتصحيح ضمن تكليفه | الخاص غير المشارك وتعديل طبقة الطالب |
| الشيخ البديل أثناء الحصة | الملخص الأدنى والحصة التي قُبل تكليفه بها | تعليم وطبقة الحصة وتقرير حصته | تاريخ الطالب الكامل وخطة الشيخ الأساسي |
| الشيخ البديل بعد الحصة | تقرير حصته فقط بالحدود المقررة | إنشاء التقرير وتصحيحه ضمن نافذة السياسة | الملخص السابق وملاحظات الطالب الخاصة وباقي الحصص |
| إدارة أكاديمية | القدر اللازم لمراجعة واعتراض وتدقيق | تصحيح موثق بصلاحية محددة وسبب | فتح كل الصوتيات/الخاص لمجرد اسم دور «إدارة» |
| خدمة خلفية | سجلات المهمة المصرح بها فقط | Job محدد وموثق | تحويل Service key إلى مسار CRUD غير مقيد |

الملخص التعليمي للبديل ينتهي **بمجرد انتهاء الحصة**. التصحيح مسموح حتى 24 ساعة من نشر تقرير حصته؛ اقتراح حماية هندسي: احتسابها من **أول نشر** وعدم تجديد المدة بكل تعديل. أجل أول إنشاء تقرير بعد الحصة يحتاج تحديدًا تشغيليًا مستقلًا؛ لا نخترع له 24 ساعة من نهاية الحصة. المرجع [#19](https://github.com/geminiamo0-ship-it/nour-elquran/issues/19).

### 9.1 قيود لا بد أن تظهر في SQL

- FK مركب للطالب مع الحصة والتقرير والتكليف والصوت؛ يمنع ربط ملف طفل بتقرير طفل آخر حتى لو كان الحساب مالكًا للاثنين.
- تقرير واحد لكل `lesson_id`؛ رقم مراجعة فريد داخل التقرير؛ مؤشر النشر لا يشير إلا لمراجعة تابعة لنفس التقرير.
- ثلاث درجات Nullable مع Check مستقل `0 ≤ grade ≤ 10`؛ لا Trigger يحوّل الغياب لصفر.
- التحقق من السورة والآية والكلمة والصفحة والطبعة من Dataset معروف. `surah ≤ 114` و`page ≤ 604` وحدهما غير كافيين.
- نطاق آيات صالح حتى لو امتد عبر أكثر من صفحة؛ منع مراجع من رواية/طبعة أخرى بلا تحويل صريح.
- ملاحظة خاصة لا تحمل Published teacher flag؛ صلاحية ونوع الطبقة يحددهما Use case والخادم، لا JSON يرسله العميل.
- `UNIQUE(aggregate_id, event_id)` للأحداث، وتفرد نتائج الدفع/الحجز/التعويض/التسليم بمفتاح العمل المناسب.
- الحجز يمنع تداخل مواعيد الشيخ والطالب داخل معاملة، مع قفل/Constraint يحمي طلبين متزامنين.
- لا تعديل/حذف عادي لإصدار منشور؛ التصحيح إصدار جديد. الحذف القانوني/الاحتفاظ له مسار موثق منفصل عن التصحيح.
- Deactivation للحساب أو التكليف يمنع صلاحيات جديدة فورًا؛ لا نعتمد على Claim قديمة وحدها.
- `created_at / published_at / submitted_at / late` مشتقة من الخادم؛ تواريخ العميل بيانات مساعدة فقط.

### 9.2 الفهارس وأنماط القراءة

| الاستعلام | نقطة البداية للفهرس/القيد |
|---|---|
| قائمة الحصص | `(learner_id, starts_at DESC, id)` مع حالة مناسبة |
| تقرير الحصة | تفرد `lesson_id` ومرجع آخر نشر على Root |
| طبقات مصحف الطالب | `(learner_id, edition_id, page)` ثم ربط بمجموعات النشر الحالية |
| الخاص في الدفتر | `(learner_id, lesson_id, updated_at, id)` |
| صندوق الشيخ | المستلم والحالة والوقت؛ لا تحميل كل الطلاب ثم فلترة بالواجهة |
| مواعيد قادمة | `(status, starts_at)` وفهرسة موارد الحجز |
| Outbox جاهز | فهرس جزئي للحالات القابلة للتنفيذ و`available_at` |
| أهلية المعلم | الطالب/الشيخ ونطاق الصلاحية مع فهارس FK |

نستخدم Cursor pagination وحدود حجم واضحة، و`EXPLAIN ANALYZE` على بيانات اصطناعية تمثل الكثافة المتوقعة. لا نحمّل تاريخ الطالب كله لعرض صفحة واحدة، ولا نعالج مشكلة N+1 بإرسال بيانات خاصة إضافية.

## 10. التفويض الخادمي وحدود الثقة

- هوية الحساب عبر مكتبة Auth موثوقة مستضافة في Workers وD1؛ تكامل Better Auth مرشح في #46 ولم يُنفذ في CF-01. لا نكتب نظام كلمات مرور/جلسات خاصًا بدل المكتبة.
- D1 داخل Bindings الخادم فقط. لا Token قاعدة للمتصفح ولا Data API عام ولا Endpoint يقبل SQL حرًا. الوصول الإداري إلى حساب Cloudflare منفصل عن حسابات الطلاب.
- لا نعتمد على سياسات RLS/GRANT أو Security Definer من PostgreSQL في D1؛ التفويض خادمي داخل Workers. العزل في كل Use case واستعلام scoped، وتدعمه FK وقيود ملكية وثوابت الطبقة، مع اختبارات منع عبر كل Endpoint.
- Roles والتكليف والموافقة من الخادم؛ لا JWT أو Cookie غير متحقق أو Header يرسله العميل يثبت الدور أو الطالب. CF-01 يرفض كل /v1/* حتى ربط Auth الحقيقي.
- مصدر المسودات وتاريخ التقارير الخام لا يظهر داخل DTO الطالب. آخر نشر فقط مع صلاحية عند الطلب، لا فلترة React لحماية البيانات.
- النشر والتسليم والحجز والرصيد وتغيير الصلاحيات Use cases محددة، بمفاتيح تكرار وVersion وسبب تدقيق. تحديث صفر صف لا يُفشل Batch تلقائيًا؛ SQL guards/constraints يجب أن تمنع الأثر الجزئي فعليًا.
- Cookies/CSRF/CORS/Origins وRate limits والتحقق من الجلسة وتجديدها وإلغائها جزء من #46. KV لا يكون مصدر الصلاحية؛ إلغاء الدور لا ينتظر Cache قديمًا.
- الاسترجاع من R2 والمشاركة والـWebSocket يفحص الطالب/الإصدار/المستلم والحالة عند كل طلب. لا مفاتيح Cloudflare أو Auth أو Provider في العميل.
- تبديل الطالب يلغي الطلبات القديمة ويعزل Query cache بالهوية والطالب والدور؛ جلسة طفل مقيدة تحتاج Scope خادميًا حقيقيًا، ولا نفترض أنها موجودة الآن.

## 11. عقد API المقترح

بادئة Versioned: `/v1`. الأسماء التالية سطح Use cases مقترح وليست Endpoints تعمل الآن. كل Response يثبت `learnerId` ونسخة المورد، وكل Request يُتحقق منه بسكيما وقت التشغيل.

### 11.1 شكل البيانات والطلبات

تفاصيل الدفتر ترجع `lesson`، و`report: null | latestPublishedReport`، و`publishedRevisionId`، و`quranScope[]`، و`editionId`، و`approvedLayerSet`، و`personalLayerVersion`، و`linkedAssignments[]`، و`archiveStatus`، و`permissions`. حقل Permissions إرشاد للواجهة؛ التنفيذ يعيد التحقق على الخادم.

النطاق: `{ editionId, surah, fromAyah, toAyah }[]`؛ الصفحات مشتقة من المصدر. الملاحظة: `id, learnerId, lessonId?, anchor, layer, authorId, kind, payload, version`. الصوت يشير لـAsset ID مصرح به، لا URL اختاره المستخدم.

المراجع والعقود الحالية في `domain.ts` و`quranAssignment.ts` و`quranAnnotations.ts` أبسط من عقد الخادم المطلوب: التاريخ النصي و`dayOffset` و`teacher` كنص و`demo:true` ليست عقود إنتاج. نضيف DTOs جديدة وMapper واضحًا بدل تغيير معناها بصمت.

### 11.2 التكرار والتعارض والأخطاء

- كل إنشاء مؤثر يستخدم `Idempotency-Key` مربوطًا بالفاعل والطالب والعملية وHash الحمولة.
- إعادة نفس الطلب تعيد نفس النتيجة؛ نفس المفتاح مع حمولة مختلفة ينتج `409`.
- `If-Match / expectedVersion` لحفظ الخاص والتقرير والتكليف؛ Version قديم ينتج `409 VERSION_CONFLICT`.
- نجاح `200/201` يعني حفظًا دائمًا؛ `202` يعني Job مقبولًا فقط، وليس ملفًا جاهزًا أو رسالة وصلت.
- `400` مدخل غير صالح؛ `401` جلسة غير صالحة؛ `403` فعل ممنوع على مورد مسموح معرفة وجوده؛ `404` لمورد غائب أو مخفي لتجنب كشف الوجود؛ `422` أدلة/مرجع قرآن غير صالح؛ `429` حد الاستخدام؛ `503` تعذر خدمة مؤقت.
- الأخطاء ترجع `code, message, requestId, retryable` دون SQL أو معلومات طالب آخر.
- قائمة Codes مبدئية: `REPORT_PENDING, VERSION_CONFLICT, ASSIGNMENT_CHANGED, REQUIRED_EVIDENCE_MISSING, SHARE_ACCESS_EXPIRED, ASSET_NOT_READY, QURAN_REFERENCE_INVALID, SNAPSHOT_NOT_READY`.

## 12. نشر تقرير الحصة — معاملة واحدة ومصدر واحد

### 12.1 الحالات

التقرير: `draft → published(r1)`. تعديل المنشور ينشئ `draft(r2)` بينما يبقى r1 هو المرئي؛ «اعتماد ونشر» الناجح يحوّل مؤشر العرض إلى r2. جميع النسخ المنشورة ثابتة للتدقيق، لكن API الطالب لا يقدم قائمة نسخ قديمة.

الحصة: حالة التشغيل مستقلة. نهاية الحصة لا تنشر التقرير تلقائيًا، ولا تمنع إثبات الحضور في انتظار التقرير.

### 12.2 خطوات الاعتماد المقترحة

1. خادم الحصة يختم نسخة التعليم عند Sequence محدد، ويحفظ JSON قابلًا للاسترداد وHash ومراجع الأصول. المحتوى المشترك للحصة منفصل عن الملاحظات الخاصة.
2. مسودة التقرير تشير إلى Snapshot جاهز ومجموعة العلامات المراد اعتمادها. لا يُقبل Publish على ملف مفقود أو حالة حية غير مختومة.
3. قبل النشر نتحقق مجددًا من صلاحية المؤلف، والطالب/الحصة، وVersion، والدرجات والمراجع؛ البديل يُفحص بوقت الخادم.
4. داخل **Batch D1 ذرية بقيود نجاح خادمية**: تثبيت مراجعة التقرير، ربط مجموعة العلامات والنطاق والـSnapshot، تحديث مؤشر آخر نشر، وربط الواجبات التي اعتُمدت صراحة، وكتابة حدث Outbox.
5. بعد Commit يقرأ الدفتر ومصحف الطالب من نفس النشر الحالي. لا ننسخ العلامات إلى جدول مستقل بلا مرجع إصدار.
6. PDF/PNG والإشعار لاحقًا. فشلهما لا يلغي تقريرًا منشورًا ولا يعرض نجاحًا وهميًا لهما.
7. عند فشل المعاملة لا يتغير المؤشر ولا تُنشر نصف الطبقات؛ إعادة نفس المفتاح آمنة.

لا توجد معاملة موزعة تجمع R2 وDO وD1. نجهّز Snapshot ثابتًا قبل المعاملة؛ الفشل بعد رفعه قد يترك Object غير مرتبط ينظفه Job بعد مهلة آمنة. فشل الرفع يبقي النشر ممنوعًا. إنشاء PDF ليس شرطًا لإظهار التقرير التفاعلي إذا كان JSON المعتمد جاهزًا.

### 12.3 التراكم والمراجعات

- L1 وL2 تظهران في مصحف الطالب عبر طبقات النشر الحالية؛ دفتر L1 يختار L1 فقط.
- تصحيح L1 إلى r2 لا يعيد إضافة r1 بجوارها. الاستعلام/Projection يختار الحالي لكل حصة، مع أثر واضح للسحب/التصحيح.
- Cache التراكم يحمل `publicationVersion`؛ تحديثه مشتق قابل لإعادة البناء. عند التأخر نرجع للقراءة الأصلية أو نوضح حداثة البيانات، ولا نخفي تصحيحًا أمنيًا خلف Cache قديم.
- ملاحظات الطالب محفوظة بمرجعها الدلالي وإصدار الطبعة. تغيير نطاق التقرير لا يحذفها ولا يعيد ربطها بآيات بالتخمين.
- تغيير طبعة/إحداثيات يحتاج Migration مختبرًا؛ المرجع غير القابل للتحويل يُعرض كحالة تحتاج مراجعة، لا فوق آية خاطئة.
- التقرير السابق ومرفقاته لا يبقيان متاحين للطالب عبر IDs مباشرة بعد التصحيح. موظف التدقيق المصرح له له مسار مستقل.

## 13. إحداثيات القرآن وطبقات الرسم

- الكود الحالي يرسم في `viewBox 0 0 1000 1594`. نُسجل `coordinateSpace/version` ونحافظ على التحويل الصحيح؛ لا نغيرها إلى `[0,1]` دون Adapter ومراجعة.
- لكل Stroke: ID، طالب، طبعة، صفحة، مؤلف وطبقة، قلم/ماركر، لون/عرض، نقاط محدودة صالحة، Operation ID ونسخة. مرجع الآية/الكلمة يُضاف عندما يكون محددًا؛ خط يمتد على الصفحة قد يكون Page-anchored.
- النص والـSVG وHit polygons موثقة ومستقلة عن Ink؛ لا حفظ لمحتوى SVG غير موثوق أرسله العميل.
- Undo/Erase عملية على العناصر المخوّلة فقط؛ Teacher cannot erase private student notes. Undo لا يحذف سجل نشر معتمد.
- نقيس حجم العمليات وحركة الرسم ونثبت حدود Batch/Points وحجم JSON من الاختبار؛ الحد الحالي المحلي 2500 نقطة للضربة ليس وحده حصة تخزين إنتاج.
- لا يكتب كل Pointer move إلى SQL؛ نرسل عمليات/دفعات مع ACK بعد دوام الحفظ في مسار الحصة.
- اختبار نفس الضربة على 360/390/768/1440px ومع Zoom وفي PDF/PNG مطلوب قبل القبول.

## 14. RealtimeKit وحالة الحصة والاسترداد

المسار المقترح للحصة: Client يتلقى Token محدودًا من API، يتصل بـRealtimeKit للصوت/الفيديو، ويتصل بخدمة حالة مصرح بها للصفحة والأحداث. RealtimeKit Data messages وحدها لا تُعامل كأرشيف دائم.

- مفتاح الحالة `lesson_id`، وParticipant IDs مجهولة، لا أسماء أطفال أو أرقام هاتف في Room identity أو Logs.
- حدث الحصة يحتوي `eventId, lessonId, learnerId, actorId, operation, baseVersion`؛ المؤلف والصلاحيات يعتمدها الخادم، ويُخصص `serverSeq` متزايد.
- `ACK` بعد الحفظ الدائم في DO SQLite إن اختير؛ Snapshot + Replay بعد آخر Sequence عند إعادة الاتصال. Event مكرر لا يضيف خطًا مرتين.
- تعارض الرسم يُحل بعمليات على IDs وترتيب الخادم؛ تعديل نفس النص يحتاج Version، ولا يستخدم Last-write-wins صامتًا لكل الدفتر.
- عند النهاية تُختم الحالة وتُسحب صلاحيات التعديل الحي، مع السماح لمسودة التقرير المصرح بها خارج القناة الحية.
- إلغاء التكليف أو انتهاء صلاحية البديل يوقف Endpoints والقناة والرسائل التالية. نتحقق من الوقت والصلاحية عند كل عملية، ونستخدم `authzVersion` أو ما يعادله لإبطال الجلسات المفتوحة.
- انتهاء JWT وحده لا يضمن إخراج عميل RealtimeKit متصل. نختبر إزالة المشارك ومنع إعادة الدخول فعليًا، بجانب منع إصدار Tokens جديدة.
- الالتحاق مجددًا بالحصة نفسها يحافظ على العمل المؤكد حفظه. العمليات غير المؤكدة تبقى معلقة أو يُعاد إرسالها بنفس IDs.
- تعطل Queue لا يفقد بيانات الحصة الدائمة؛ Outbox يُستأنف. تعطل الخادم/DO يُختبر بإعادة التشغيل، ولا نفترض أن الذاكرة كافية.
- لا تسجيل A/V ولا Egress تسجيل تلقائي؛ حق تسجيل التسميع المختار في تدريباتي منفصل تمامًا.

## 15. الملفات والصوتيات والخصوصية

### 15.1 فصل الأغراض

| الغرض | الوضع |
|---|---|
| تلاوات القرآن المرجعية | مصدر مرخص مستقل، لا بيانات طالب |
| تسميع ذاتي محلي | موافقة ميكروفون، تشغيل/مسح على الجهاز؛ لا رفع تلقائي |
| مسودة صوت على الخادم | تحتاج موافقة احتفاظ صريحة، وتبقى خاصة |
| دليل واجب/تسميع مشارَك | Asset محدد يُرفق بتسليم/مشاركة صريحة للشيخ المخوّل |
| تعليق صوتي للشيخ | Asset خاص مرتبط بالمراجعة والطالب، وفق المتطلبات المعتمدة |
| صوت/فيديو الحصة المباشرة | غير مسموح بتسجيله ضمن القرارات الحالية |

### 15.2 دورة الرفع المقترحة

1. Request لإنشاء Upload intent يحدد الطالب والغرض والحجم والنوع، وموافقة صالحة عند الحاجة.
2. يخصص الخادم Object key عشوائيًا خاصًا بالمستخدم والغرض؛ لا يقبل مفتاح R2 أو URL يحدده العميل.
3. رفع إلى منطقة مؤقتة/حجر، ثم Finalize يفحص وجود الملف والحجم والنوع الفعلي والـChecksum/Metadata الموثوقة وسلامة المحتوى حسب نوعه.
4. لا يصير الملف صالحًا كمرفق إلا بعد حالة `ready`. Upload URL أو HTTP نجاح وحده ليس تسليم واجب.
5. تسليم/مشاركة يثبت قائمة Asset IDs المختارة ونطاقها والمستلم؛ باقي الصوتيات تظل خاصة.
6. Upload غير مكتمل أو غير مرتبط ينتهي وينظف وفق سياسة محددة. إعادة Finalize لا تنشئ ملفًا ثانيًا.
7. التشغيل والتنزيل عبر بوابة تتحقق من الصلاحية وتدعم Range للصوت؛ لا Public bucket للصوتيات أو دفاتر الأطفال.

روابط R2 الموقعة وحدها تحمل صلاحية حتى انتهائها. للمحتوى الذي يتطلب سحب وصول فوريًا — خصوصًا ملخص البديل أو مشاركة ملغاة أو إصدار تقرير سابق — نستخدم Endpoint يتحقق من كل طلب، ولا نعتمد على رابط مباشر طويل العمر. أي روابط أخرى قصيرة العمر تحتاج TTL مدروسًا؛ انتهاء الوصول لا يمحو ملفًا سبق تنزيله.

### 15.3 الاحتفاظ والحذف

- نحدد قبل الرفع الحقيقي مدة مسودات الصوت، والتسميعات المرسلة، وصوت الشيخ، والمشاركات والتصديرات والنسخ الاحتياطية؛ لا نخترع مدة واحدة لكل الأنواع.
- سجل موافقة بالفاعل والغرض والوقت وإصدار النص؛ موافقة WhatsApp لا تُجيز تسجيل صوت الطفل. نتحقق من TLS والتشفير أثناء التخزين وإدارة المفاتيح قبل قبول الخدمة.
- Logs تستخدم IDs وCodes؛ لا نص تقرير أو ملاحظة أو صوت أو هاتف/اسم طفل داخل Logs أو GitHub.
- Immutable للمعاملات والمراجعات يعني منع التعديل الصامت؛ لا يعني الاحتفاظ الأبدي ببيانات الطفل. الحذف/الاحتفاظ المعتمد يزيل المحتوى الشخصي من R2 والنسخ المشتقة، مع أثر تدقيق محدود لا يعيد بناء المحتوى.
- عند حذف/إغلاق طالب لا نستخدم Cascade أعمى يمحو مستندات مالية أو يسرب بقايا Shared URLs؛ مسار حذف قابل للتتبع بعد تحديد السياسة.
- تصدير بيانات الحساب والتحقق من طلب الحذف وإدارة النسخ الاحتياطية يدخل في #56.

## 16. الواجبات والتسميع — الربط مع تدريباتي

الدفتر يشير إلى الواجب ولا يحل محله. كل Assignment يحمل الطالب وإصدار التكليف ومصدر الحصة/التقرير إن وجد. نموذج التكليف يتضمن نوع العمل والنطاق ومتطلب الدليل: صوت إلزامي أو إجابة كتابية أو تأكيد إنجاز، حسب اختيار الشيخ.

- نشر التكليف: Draft → معاينة → نشر صريح؛ تعديل المنشور إصدار جديد وإشعار بالتغييرات.
- الطالب يحفظ Draft ناقصًا بلا مشاركة؛ لا يُسمح بالتسليم النهائي مع أدلة إلزامية ناقصة.
- قبل «تسليم الواجب» تظهر نسخة التكليف والأجوبة والصوتيات والملاحظات المحددة والمستلم.
- التسليم ينشئ محاولة ثابتة؛ الحالة لا تصبح «تم التسليم» إلا بعد حفظ المعاملة.
- الشيخ يراجع المحاولة ويطلب تعديلًا أو يُنهي المراجعة. إعادة التسليم بعد طلب الشيخ تنشئ v2 ولا تستبدل v1.
- تعديل التكليف لا يعيد فتح كل تسليم تلقائيًا؛ طلب الإعادة إجراء منفصل وصريح.
- التسليم المتأخر مقبول مع وقت الخادم وLate flag، وليس مرفوضًا تلقائيًا بانتهاء الموعد.
- عند تغير إصدار التكليف أثناء إعداد الطالب، يعيد الخادم `ASSIGNMENT_CHANGED` ويطلب معاينة النطاق الحالي قبل التسليم؛ المحاولات السابقة تظل على إصدارها.
- الصوت مرتبط بالآيات وبمحاولة محددة؛ مراجعة التسميع ليست درجة رسمية تلقائيًا.
- واجب جديد لا يُنشر لمجرد أن AI اقترحه أو انتهت حصة.

## 18. Outbox والإشعارات والمهام

- كل معاملة تنشئ حدثها في Outbox داخل نفس قاعدة البيانات/حدود التخزين التي ثبت فيها التغيير؛ لا `commit ثم send` بلا سجل استعادة.
- Dispatcher يتابع `available_at / attempts / lease`، ويرسل Event ID ثابتًا؛ Consumer يسجل المعالجة قبل الأثر المتكرر المناسب.
- Queue قد تعيد التسليم؛ الحماية بمفتاح عمل فريد، لا وعد Exactly-once عام.
- ترتيب التحديثات يعتمد `aggregateVersion`؛ حدث قديم لا يعيد نشر تقرير أو موعد سبق تغييره.
- Job التذكير يحمل `lessonId + scheduleVersion + stage + recipient + channel`. قبل الإرسال يعاد فحص التأكيد والموعد والصلاحية والموافقة والفئة.
- التذكيرات المعتمدة: 24 ساعة و1 ساعة قبل الحصة؛ WhatsApp قبل ساعة للشيخ والمستفيد المعني إذا كان Opt-in والقالب صالحين. التجديد: 7 أيام و24 ساعة قبل الانتهاء.
- تغيير/إلغاء الحصة يبطل التذكيرات القديمة؛ المنع بفحص النسخة والحالة عند Dispatch، وليس حذف Job وحده.
- موافقات WhatsApp منفصلة حسب الفئة؛ الهاتف وحده ليس موافقة. تجميع تذكيرات الأشقاء لنفس المستلم/التوقيت وفق المتطلبات، دون خلط المواعيد أو كشف بيانات غير لازمة.
- تذكير الحصة المجدول يتبع الاستثناء المعتمد لساعات الهدوء؛ لا نعممه على رسائل أخرى.
- Provider acceptance، Delivery، Failure حالات مختلفة؛ لا نعرض «وصلت» لمجرد قبول Provider الطلب.
- Backoff وDead-letter queue وأداة Replay آمنة وسجل فشل. فشل WhatsApp لا يوقف الحصة أو نشر التقرير؛ الإشعار الداخلي مستقل.
- لا Grades أو أخطاء أو صوتيات أو ملاحظات خاصة في WhatsApp.
- انقطاع بعد قبول Provider وقبل حفظ النتيجة يعالج بمفتاح Provider إن دعمه أو Reconciliation؛ لا Retry أعمى يضمن عدم التكرار بلا دليل.

المرجع [#54](https://github.com/geminiamo0-ship-it/nour-elquran/issues/54)، [#17](https://github.com/geminiamo0-ship-it/nour-elquran/issues/17). تنفيذ الربط لا يصرح بإرسال رسائل فعلية ضمن مهمة التخطيط الحالية.

## 20. سيناريو قبول متصل

1. حساب تجريبي اصطناعي له الطالبان A وB، وشيخ أساسي لكل تكليف موثق.
2. حصة L1 تخص A، وتقريرها Draft: لا درجات أو علامات Draft في الدفتر أو المصحف.
3. الشيخ ينشر r1: يظهر تقرير L1 ونطاقها وعلاماتها في دفتر A؛ المصحف العام يعرض نفس الطبقة.
4. ينشر L2: المصحف يجمع L1 وL2؛ دفتر كل حصة يعرض طبقتها فقط.
5. A يضيف ملاحظة خاصة لـL1؛ لا تظهر للشيخ. يشارك ملاحظة محددة بعد المعاينة، فتظهر نسخة الاختيار فقط.
6. الشيخ يصحح L1 وينشر r2؛ الطالب يرى r2، وتبقى ملاحظته الخاصة ومصادرها، ولا يظهر r1 بتغيير URL.
7. الواجب المرتبط يفتح في تدريباتي؛ يسلم الطالب صوتًا مختارًا بعد اكتمال الأدلة؛ الشيخ يطلب تعديلًا ويفحص v2 مع بقاء v1.
8. تبديل B يزيل طبقات A وطلبات A المعلقة؛ لا تتسرب Response أو Cached PDF إلى الصفحة الجديدة.
9. بديل مقبول يدرّس حصة معينة؛ ينتهي ملخصه عند النهاية، ويعدل تقريرها فقط داخل نافذته، ثم يرفض الخادم المحاولة المتأخرة.
10. Refresh أو إعادة اتصال لا يفقد أي عملية سبق تأكيد دوام حفظها. انتهاء/إلغاء صلاحية يمنع الوصول حتى عبر رابط محفوظ.

## 22. الأداء والتشغيل والإطلاق

- نقيس زمن List/Notebook/Publish وحجم الصفحة وعدد الاستعلامات وحجم الطبقات، ثم نحدد SLO وسعة الغرف المتزامنة المعتمدة قبل #50/#56. لا نستخدم نتائج Royal Bank كدليل أداء لنور القرآن.
- Load test يفصل قراءة الدفتر عن نشر تقارير وعن الرسم وعن WebRTC. تبدأ التجربة بعميلين ثم تتدرج للسعة المستهدفة وفق ميزانية الاختبار.
- Metrics: API errors/latency، تفويض الخادم denies، Outbox age، Queue retries/DLQ، حفظ الرسم وReplay lag، Export failures، Object orphans، Provider delivery وBooking conflicts.
- Alerts على فشل الحفظ أو تأخر الأعمال والملفات/الأرصدة غير المتطابقة؛ Dashboards بلا نصوص أطفال.
- Restore rehearsal يشمل DB وManifest الأصول والـSnapshot blobs؛ وجود Backup وحده لا يثبت الاستعادة. أهداف RPO/RTO تُعتمد وتُختبر قبل التشغيل الحقيقي.
- Development وStaging وProduction منفصلة؛ بيانات اصطناعية فقط في GitHub وStaging العام.
- Feature flags وظيفية: API adapter/دفتر حقيقي/رفع صوت/مشاركة/Export/حجرة RealtimeKit/WhatsApp؛ لا ضرورة لمزود Flags جديد. الوصول يظل مفروضًا بالخادم حتى مع إخفاء الواجهة.
- الإطلاق تدريجي بحسابات اختبار ثم مجموعة محدودة وفق خطة تشغيل؛ لا تُفتح ميزة صوت أو دفع أو مشاركة قبل قبول سياساتها واختباراتها.
- Rollback للتطبيق مع Migrations بأسلوب Expand/Contract؛ لا Downgrade مدمر أو حذف تقرير/رصيد لإصلاح خطأ. نوقف ميزة أو Job متعطلًا ونحافظ على البيانات والأحداث لإعادة التشغيل.
- نموذج التكلفة قبل الإطلاق يحسب دقائق RealtimeKit، التخزين الصوتي والتصديرات، طلبات API/DO، الرسائل، قاعدة البيانات والـBackup. لا أرقام اشتراك أو تحمل مجاني غير موثقة هنا.

## 24. تعريف اكتمال الباك إند لهذه الرحلة

تكتمل الرحلة عندما تنجح في Staging بهويات حقيقية مضبوطة: حصة موثقة → تقرير شيخ معتمد → طبقة تراكمية في المصحف وطبقة حصة في الدفتر → ملاحظات خاصة ومشاركة محددة وفق سياستها → واجب وتسليم ومراجعة → أرشيف قابل للاسترداد، مع منع جميع مسارات الوصول غير المصرح بها وتوثيق نتائج الاختبارات على نفس SHA.

تشغيل دفاتر حقيقية لا يستلزم انتهاء AI. تشغيل حصص مدفوعة يستلزم قبول الحجز والحضور والرصيد والدفع وسياساتها. لا نصف ميزة بأنها Production-ready بسبب Mock جيد أو CI واجهة فقط.
