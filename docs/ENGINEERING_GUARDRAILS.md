# Engineering guardrails

## Boundaries
- Presentation (Next.js/React) → validated network contracts → API/Use Cases → domain → infrastructure adapters.
- UI components do not call Supabase service-role APIs, Durable Objects, queues, OpenRouter, or LiveKit signing secrets directly.
- Separate teachers, learners, account owners and admins; **account identity is not student identity**. Every student data request must authorize profile ownership or explicitly delegated teacher/admin access.
- Teacher/lesson/scheduling/financial state differs from learner-local state; no cross-DO distributed transaction assumptions.
- Postgres transactions enforce shared resource invariants and payment ledger. Idempotency is mandatory for reservations, webhooks and retries.
- Durable Objects may own authorized hot interactive state; writes saved in SQLite and outbox atomically. Queue at-least-once deliveries require dedupe in downstream consumers.
- A 30-minute live class is a LiveKit connection, not a long-held Worker/DO request. Do not proxy media through Workers.
- Quran canonical text never generated by AI. Quran source/recitation permissions and riwayah must be recorded; versioned references verified.
- LLM plans are UNTRUSTED. Only permit predefined exercise types with schema validation, surah/ayah bounds, approved curricular range and teacher approval before publishing.
- Speech recognition and tajweed error detection are non-authoritative until measured against teacher-labelled samples; show uncertainty.
- Child audio/video recording off by default; require appropriate consent and retention/deletion rules.
- Strict TS, typed errors, centralized constants, secure env storage, minimal dependencies, small cohesive modules, no giant handlers.
- All schema changes through migrations; no direct production mutation.
- Structured logs with safe IDs; never log children’s content, secrets, audio, email or full student records.
- Security and relevant tests must be part of same issue/PR. Document all architectural deviation by ADR.

## Frontend phase
Mock API/fixtures behind stable interfaces; **no fictitious backend state described as implemented**.
Mock profile switch may be local; real authorization and billing must wait for backend phase.
RTL and mobile first (including classroom keyboard/touch and limited network) are non-negotiable.
User-facing medical, legal or religious authority claims must be avoided; teacher remains responsible for religious/tajweed assessment.

## Review questions
Are permissions explicit? Are contracts runtime-validated? Are student records isolated? Is Quran text grounded? Does this introduce secrets, operational overhead, and failure modes? Is the testing plan measurable? Are the issue and status updated?
